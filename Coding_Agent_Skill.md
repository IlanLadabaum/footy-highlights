This document is curated by the developer, and meant to be a skill file that transcends a specific project/repo. Follow these instructions in order to adhere to the developer's desires in this project. Do not edit this file without explicit approval, and do not add any project-specific information to this file.*

# How to work for this developer

## Planning Documents

Before implementing any code, planning documents should be created in the Plan directory. These will be created by conversation with the user, and should serve as a running log of design choices, and current status. Items should be labeled as [BUILT], [DECIDED], [OPEN], [PROPOSED], and any other similar-style status marker that fits as a description. Only items that are marked [DECIDED] should be built by an agent, and questions that are not decided should not be decided by an agent, but rather posed as a question for the user to decide. The [DECIDED] tag can only be used to refer to user-approved design choices. The agent does not have the authority to decide design choices on their own. The agent may note its own ideas/research as [PROPOSED] ideas, but it may not switch the flag to [DECIDED] without user approval. The [OPEN] flag is used when a design choice has been raised, but not yet decided. Where relevant, the possible options, and discussed pros/cons, should be recorded.

In order to maintain a reasonable size and scope of planning document, these will be hierarchically nested. Beginning with one general overview plan describing the project in broad terms, and containing markers to specific planning documents containing the specific information for each aspect of the project. Documents should be roughly separated by relevant topic, in order to best focus the context for future agents working on specific features in the future.

As an agent is working, whether it be planning through a discussion with the user, researching possible solutions, implementing code, or any other productive task, the agent must keep the relevant planning docs up to date with the current status of research, decisions (including rationale where relevant, for future auditing purposes), and implementation/testing progress.

Despite separating planning documents by hierarchy, scope, and task, some documents may grow long as a result of growing records, decisions, and stale information. The agent should periodically ensure that the planning documents are free of redundancies and stale/outdated information. The agent should err on the side of caution, preserving/keeping information if it may be useful in the future, while reducing the size of the planning docs where possible by removing redundant and/or outdated information.

## Planning Skills

When planning, the agent should engage in a back and forth with the user about the specific topic/design at hand, recursively drilling down with questions, starting from the global vision, and ending up with the nitty gritty details. For each planning session, there should be an established scope - what specific point/feature are we trying to plan? This way, there is a clear point where a user/agent can determine "we have finished the plan for this section." Do not switch from Planning mode/mindset to engineering without approval (i.e. wait for approval before beginning to build).

Where you see gaps in the plan that pertain to the discussion, move the conversation forward to fill in these gaps, if there are not already items of discussion to follow up on. This could be by simply pointing out where the gaps are and what they signify, or also by suggesting your own ideas for how to fill the gaps.

## Engineering Skills

Do not build any features that are not yet [DECIDED]. If a detail is not decided and is a blocker, switch back into planning mode until the blockers are cleared.

In general, the agent is trusted to be a better engineer than the user. This means, while details about functionality and design must be approved and decided by the user, details about technical implementation are less strictly regulated, and specific technical implementations may be chosen by the agent. This does not grant license to override the design decisions.

If an agent has been explicitly told to build an aspect of the project, the agent should raise the open questions that remain within the scope of that request. If (and only if) the user chooses to proceed anyway, the agent has license to make design decisions, insofar as they are necessary in order to fulfill the specific scope of the task explicitly asked for by the user. This license does not apply to decisions that are non-blocking details, or that fall outside the scope of the user's request. In this case, as well as any engineering context, the agent must maintain and report a log of decisions and deviations as follows:

When engineering, if the agent for any reason chooses to deviate from the chosen plan, in any way, the agent must document and report this to the user, logging all deviations in a DEVIATIONS.md file, and pointing the user to the location of this file when finished. If a blocking decision needed to me made to fulfill the user's request, the agent should log all of the non-[DECIDED] (agent made) choices in a "Decisions" section of DEVIATIONS.md. A summary of the document, highlighting the most important elements, must be presented to the user as part of the engineering summary handoff. If the user responds answering/clarifying whether the deviations/decisions were correct/incorrect, these choices should be logged in the planning documents, and the relevant items removed from DEVIATIONS.md. DEVIATIONS.md, as such, is meant to serve as a live record of agent choices, as yet unreviewed/unspoken on by the user.
